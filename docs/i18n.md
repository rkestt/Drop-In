# i18n IT/EN (#64)

Stato al 2026-11-16 (Phase 4B, lane i18n, opzionale): **fondazione pronta, UI
non migrata**. L'app resta italiana, ma dizionario, detection e forma degli
URL esistono e sono testati. #64 resta aperto: si chiude quando almeno le
superfici core girano in due lingue con routing.

## Decisione

**Non adottiamo `next-intl` adesso, e non aggiungiamo il prefisso di locale.**

| Opzione | Costo | Beneficio ora | Verdetto |
|---|---|---|---|
| `next-intl` + `app/[locale]/**` | sposta tutte le route sotto un segmento dinamico, middleware di negoziazione, `generateStaticParams`, hreflang, aggiornare ~60 selector e2e e gli snapshot visivi | una sola lingua reale (utenti a Roma), nessuna richiesta di utenti EN | rimandato |
| `react-i18next` | runtime client, provider, suspense, bundle | nessun routing | no |
| custom minimale (scelto) | 3 file + test | dizionario tipizzato, fallback, detection, `localePath` pronti | sì |

La fondazione esiste perché la migrazione sia meccanica, non perché si
traduca tutto: estrarre le stringhe senza routing darebbe un'app che finge di
essere multilingua (metà testi tradotti, metà no) — peggio dell'italiano
coerente.

## Cosa c'è

| File | Contenuto |
|---|---|
| `lib/i18n/config.ts` | `LOCALES` (`it`, `en`), `DEFAULT_LOCALE`, `isLocale`, `resolveLocaleFromAcceptLanguage` (q-values, regioni, `*`, `q=0`), `localePath` (IT senza prefisso, EN sotto `/en`), cookie `NEXT_LOCALE` |
| `lib/i18n/messages.ts` | dizionario core (nav, auth, azioni, errori, a11y, check-in, lobby, recensioni, empty state). `it` è la fonte; `en` deve avere le stesse chiavi (test) |
| `lib/i18n/index.ts` | `translate(locale, key, params)`, `translator(locale)`, `interpolate`, re-export di config e dizionario |
| `tests/unit/i18n.test.ts` | 10 test: chiavi allineate, nessuna stringa vuota, interpolazione, fallback, `Accept-Language`, path |

Regole d'uso:

- Segnaposto `{nome}`, mai concatenazioni: l'ordine delle parole cambia.
- Una chiave assente in EN cade sull'italiano; assente anche in IT restituisce
  la chiave (il buco si vede) e in dev lo segnala una volta.
- Le stringhe lunghe (legale, onboarding, copy di prodotto) restano nei
  componenti finché non c'è la review di copy per lingua.

## Strategia URL (quando si attiva)

- Italiano **non prefissato** (`/`, `/courts/x`): URL storici, link condivisi,
  QR e indicizzazioni restano validi. L'italiano è il default, non una lingua
  “speciale”.
- Inglese sotto `/en` (`/en`, `/en/courts/x`), gestito da `app/[locale]/…` con
  `generateStaticParams` per le pagine statiche.
- Prima visita senza cookie: `Accept-Language` (`resolveLocaleFromAcceptLanguage`),
  poi redirect **solo** per utenti umani; i bot restano sulla lingua dell'URL
  (niente cloak/redirect loop).
- Scelta esplicita: cookie `NEXT_LOCALE` (1 anno, tecnico) + `<link rel="alternate" hreflang>`
  su ogni pagina, `x-default` sull'italiano.
- `localePath` è già la funzione che genera i link: usarla, non comporre
  stringhe a mano.

## Piano di migrazione

| Fase | Cosa | Criterio di done |
|---|---|---|
| 1 (fatta) | dizionario, detection, `localePath`, test | `npx vitest run tests/unit/i18n.test.ts` verde |
| 2 | `app/[locale]/**` + middleware, `/en` servito, hreflang, switch in Impostazioni | `/en` rende le stringhe del dizionario, `/` invariato, redirect testati |
| 3 | estrazione per superficie: nav/auth/errori → check-in → lobby → recensioni → profilo | ogni superficie ha le chiavi in IT+EN e un e2e che passa con `?lang`/path |
| 4 | email e notifiche | template auth con testi per lingua; corpi DB valutati caso per caso |
| 5 | legale e testi lunghi | review legale/copy per lingua, `docs/legal/README.md` aggiornato |

Fuori scope finché non c'è una richiesta reale di utenti EN: user-generated
content (recensioni, nomi dei campi) e testi legali.

## Test

```bash
npx vitest run tests/unit/i18n.test.ts
```

Copre: parità chiavi IT/EN, nessun valore vuoto/TODO, interpolazione e
segnaposto ignoti, fallback lingua/chiave, header `Accept-Language` (regione,
q, `q=0`, lingue non supportate, header assente), `localePath` IT/EN.

Quando arriva il routing: gli e2e vanno parametrizzati per locale (stessi
flussi, `baseURL + /en`), non duplicati a mano; gli snapshot visivi si fanno
per lingua solo dove il testo cambia il layout (360px, stringhe lunghe).

## Aperti

- Decisione di prodotto: c'è domanda per l'inglese? Se no, la fondazione
  resta e #64 si chiude come “non necessario ora”.
- `next-intl` va valutato di nuovo alla fase 2 confrontando bundle e API con
  la soluzione custom (se il dizionario supera ~300 chiavi con plurali e date,
  una libreria conviene).
- Notifiche: i corpi sono salvati in italiano nel DB (`push_notifications`):
  localizzarli richiede salvare chiave+parametri, non testo.
